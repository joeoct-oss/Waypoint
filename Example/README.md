# Waypoint example app

Orbit Shop, a small shop that behaves like a production app, so every navigation pattern shows up in a real journey:

1. **Splash**, then the main tabs, the same for guests and signed-in readers.
2. **Accounts**, asked for only when an action needs an account (Check out, Save, Orders, Wish list, or Sign in on Account): a sheet over the tabs whose first line says why it opened (such as "Sign in to check out. Your cart stays as it is."), with Sign in (a wrong password shows an error; Reset password is a sheet that turns into Link sent) and Create an account (three pushed steps: your details, a password with the terms as a sheet, and the 6-digit code from the email, with Send a new code; going back keeps what was typed). Once the reader signs in, the sheet closes, a "Signed in as" toast says what carries on, and the action carries on; Cancel drops it. Sign out shows a "Signed out" toast. A mock auth service stands in for a server: any email and password sign in, except the password `wrong`.
3. **Main tabs** (system tab bar): **Shop** (the "Nebula nights" collection banner, products picked as cards and the rest as rows, a pushed collection or product, filters and the wish list as sheets, and, while the cart has products, "Your cart is waiting", whose Go to cart runs one `TabRouter` transaction that selects Shop and sets its path to the cart's first product with the cart above it, so the reader sees one change and Back goes to the product; a fast double tap on a row pushes once), **Search** (a search field at the top of the list, with recent searches and categories before typing and a result count after), a product with Share and Save in the bar and a Reviews row, where Save shows a small "Saved to your wish list" sheet whose View wish list swaps it for the wish list in one transaction, **Cart** (a badge with the cart's count; subtotal, shipping and total, or "Your cart is empty" with Browse the shop; checkout presented full screen on its own Waypoint stack: pick a saved address or push Add a new address, then Payment and Review, then Order placed, which replaces the steps in one `setPath` so Back can't return to Review, and whose Continue shopping closes checkout and opens Shop) and **Account** (the profile, or for a guest "Sign in or create account"; Orders and Wish list with their counts, or "Needs an account" for a guest; saved addresses with Add a new address; Settings with App, Developer, About and Sign out, which goes back to Account as a guest). Orders list each order's number, status line and total, and an order shows its items under a Placed, Shipped, Delivered timeline.
4. **Developer**, under Account > Settings: Clear all data, which asks to confirm, then empties the store and starts the app over as a fresh install; and the **Navigation Lab**: two branches, SwiftUI and UIKit, each launching five demo flows (login, tabs, detail push, sheet and deep link) as a SwiftUI flow or a UIKit flow. These twenty entry points are also UI test scenarios. Three of the SwiftUI branch's SwiftUI entries run for real: Detail push; Tabs, whose tab container starts with Shop and Search and can bring back all four tabs with `TabRouter.setTabs(_:)`, keeping the selection when its tab stays and falling back to Shop when it goes; and Sheet, which picks the next sheet's size and whether a swipe closes it, presents a sheet or a full-screen cover, and on each level offers Present on top, Dismiss (through the router that presented it), Dismiss flow (through its own router) and Dismiss all, with the story router's tree on its screen. The others open a placeholder. Below them, **Views and view models** has one screen per story of that epic: Navigation style tries the demo product with outputs, an injected `FlowNavigator` or `@FlowNavigation`; Navigate after the flow is gone shows a view model's late push return `.ignored`; A wrapper with no router above it shows `@StackNavigation`'s `noRouterInScope` failure; and Preview a screen without the app shows `.waypointPreview(flow:)`. Each demo runs full screen: the product demos on a Waypoint stack of their own, and the no-router demo in a plain SwiftUI stack. Under them, **Lab tools** has the event log, which lists every navigation call and its outcome (`EventLog`, filled by `EventLogHandler` from the routers' log), and the navigation tree as text.

Every pushed screen shows its route trail, read from its stack router by `RouterTrail`: the main tabs, the tab or the flow that presented the stack, then each route by its display name, so a product on Shop reads `main › shop › orbit lamp` and checkout reads `main › cart › checkout`. From iOS 26 the trail is the navigation bar's subtitle; earlier systems show it as a strip below the bar.

Sheets take their sizes from Waypoint's `SheetOptions` (`AppSheets`): the main tab router sets the app's defaults once with `setPresentationDefaults(_:)` (medium and large, opening at medium), and Reset password takes them with a bare `.sheet`. The filters open at medium and grow to large, sign in and the wish list are large, the saved sheet fits its message, and the terms hide the drag indicator and can't be swiped away. Shop's Wish list button opens the wish list as a sheet for anyone; its "You may also like" Save asks a guest to sign in over the wish list, so the wish list's router presents the accounts flow two sheets deep. Signing in there saves the product at once and pushes Signed in, whose Done closes both sheets in one change with `dismissAll`; Cancel closes only sign in. The wish list's Done closes its flow with `dismissFlow` on its own router, and the saved sheet's Close calls `@DismissFlow` from the view. `SheetOptionsModifier` turns a presentation's options into SwiftUI's sheet modifiers until Waypoint draws sheets (#12), so no screen sets a size of its own.

The `App` asks for each window's view with `AppCoordinator.makeWindow(services:launch:)`, which makes a new app coordinator for every window. The services (the local store, the session and the mock auth service) are made once and shared by every window; the store keeps the session, cart and wish list between launches. The whole app's navigation runs on Waypoint: one `TabRouter` holds the Shop, Search, Cart and Account tabs with one stack around them all (`stacks: .shared`), which `MainTabView` draws with `WaypointStack` around the `TabView`, and every sheet and cover is a flow a router presents: the tab router presents the accounts flow, whose router pushes Create account's steps and presents Reset password and the terms; the Shop and Search routers present the filters, the saved sheet and the wish list, which View wish list swaps in with one transaction; and the cart's router presents checkout full screen. The tab bar, the sheets and the cover are still SwiftUI's `TabView`, `sheet` and `fullScreenCover`, bound to the routers, until Waypoint draws tabs and presentations itself, and the app's root switch waits for `WaypointRoot`. A product page links to a related product with `WaypointLink`, which pushes through the same router. Every stack router logs navigation issues at `.error` and above to a shared issue log, which shows the newest one in a banner over every tab and every pushed screen. The main tab router sets two fallbacks every flow inherits (`NavigationRules`): going back to a screen that isn't in the stack pops to the root, and a present while a flow is up replaces it. The configuration's `onNavigationFailure` counts the calls no fallback recovered. Settings > Navigation rules shows that count and the queued-call limit, has a toggle that lets the same push go through twice (`setDuplicatePushRule(.allow)`) with Open Orders twice to try it, and has Go back to Orders and Open sign in twice, which try the two recovered calls. The same routers write to the unified log under the `dev.waypoint.example.waypoint` subsystem, from `.info` up with route values in debug builds: one journey box for each change the reader sees, titled such as `🧭 PUSH ▸ ProductDetailView`, with the coordinator, the tab, the previous screen and the whole app as a tree. Each coordinator names its router with `router.setCoordinator(self)`. Set `.debug` in `AppServices` to add a box with every field of each visit and the routers' own lines. Their `transaction` and `push` intervals go to Instruments as signposts (`AppLogHandler`). Every product has an illustration drawn in SwiftUI from the design canvas's artwork (`ProductIllustration`), so the only image asset is the app icon: the identity's day icon, and its night icon in dark mode (`Resources/Assets.xcassets`). A pushed screen covers the tab bar, and the bar slides away with the tab's root, as `hidesBottomBarWhenPushed` does in UIKit, with no code for it: the stack is around the tabs. Selecting another tab pops the stack, so each tab opens at its root. Each route type has one destination on the `TabView`, and the selected tab's coordinator draws it. The tab roots' titles and Shop's Filter and Wish list are set on the `TabView` for the selected tab, since a screen inside it can't reach the bar. For the same reason, Search draws its own search field: the system's `searchable` shows no field for it there. Screens report what the reader did through callbacks; only coordinators navigate. Bars, tab bars, sheets and buttons are system controls, so they take Liquid Glass on iOS 26 and the classic look on earlier systems.

## Generate and run

The Xcode project is generated with [Tuist](https://tuist.dev) from `Project.swift`; no `.xcodeproj` or `.xcworkspace` is committed. The app takes the Waypoint package through Tuist's package integration (`Tuist/Package.swift`), which `tuist install` resolves; Tuist then also writes the package's own project, `Waypoint.xcodeproj` and `Derived/`, into the repository root, where git ignores them. Its version is pinned in `.mise.toml`; see [Setup](../CONTRIBUTING.md#setup).

```sh
tuist install --path Example
tuist generate --path Example --no-open
open Example/WaypointExample.xcworkspace
```

`scripts/test-mac.sh full` generates the project and runs the unit tests (`WaypointExampleTests`, Swift Testing, for the view models, the services container and the store) and the UI tests on the project simulator, then runs `SystemLinkTests` and `MissingDestinationTests` again in the release configuration. `scripts/test-mac.sh --only WaypointExampleUITests/StackTests` runs one class or test; see [Run a Mac tier](../TESTING.md#5-run-a-mac-tier) for the steps and [Where each test runs](../TESTING.md#1-where-each-test-runs) for the tiers.

## Launch arguments

UI tests start where they need to: `-clearData YES` starts from a fresh install (the UI tests always pass it), `-signedIn YES` starts signed in, `-lab YES` opens the Navigation Lab, `-branch uikit -flow sheet -kind swiftui` opens one Lab entry, `-splashSeconds 0` skips the splash (the UI tests pass it unless they ask for a splash) and `-splashSeconds 5` holds it long enough for a test to see it, `-shopPath 1,2,3` pushes those products onto the shop in one change, `-shopFollowUp pop` (or `popToRoot`, `link`) makes one more change 150 ms into that push, `-systemLinks YES` draws the product page's related link as a system `NavigationLink`, `-missingDestination YES` makes that link push a reviews route that the registry lists but no products screen draws, and `-labReviewsSeconds 8` makes the Lab's demo reviews take that long to load. `ExampleApp.launch(signedIn:lab:branch:flow:kind:splashSeconds:shopPath:shopFollowUp:systemLinks:missingDestination:labReviewsSeconds:)` in the UI tests sets them. `JourneyTests` has one test for each journey on the design canvas, `StackTests` checks the shop's Waypoint stack and its Waypoint link, `SystemLinkTests` checks that a system link is refused and reported, in the release configuration too, `MissingDestinationTests` checks the screen and report for a route with no destination in its stack, in both configurations, `LabTests` covers every Lab entry, and `ViewModelStyleUITests` covers the Views and view models stories.

## Folders

| Folder | What it holds |
|---|---|
| `App/` | The `App`, the app coordinator and its roots, and launch arguments |
| `Dependencies/` | `AppServices`, the one container the `App` makes, and one dependency struct per feature (`ProductsDependencies`, `CartDependencies`, `AccountDependencies`, `AuthDependencies`, `LabDependencies`) listing what that feature uses. The coordinators still take their services one by one until they move onto these structs (#59, #301) |
| `Services/` | The local store, the session, the saved addresses, the auth service protocol and its mock, and the issue and event logs |
| `Store/` | The product catalog (`ProductCatalog`, with `SampleCatalog` for the fixed sample products), orders, and the account type |
| `Flows/Splash/` | The splash screen |
| `Flows/Auth/` | The account gate, and the accounts sheet: sign in, the create account steps and the reset password sheet, with their coordinator |
| `Flows/Main/` | The main tabs and their coordinator |
| `Flows/Products/` | Shop and Search: the collection banner, the cart card, product cards and rows, a collection, a product, the cart pushed by Go to cart, the filter and wish list sheets, and Search's view model (`SearchModel`), which pushes through a navigator scoped to `ShopFlow` |
| `Flows/Cart/` | The cart and the full-screen checkout |
| `Flows/Account/` | Account, orders, settings, and the Navigation Lab's place in the account stack |
| `Flows/Lab/` | The Navigation Lab: both branches, the Detail push flow (`DetailPush/`), the Tabs and Sheet stories (`TabsDemo/`, `SheetDemo/`), the placeholder each other demo flow shows until it is built, the Views and view models demos (`ViewModels/`), and the Lab tools (`Tools/`): the event log and the navigation tree |
| `Resources/` | The asset catalog with the app icon |
| `Catalog/` | The Lab's branches, flows, kinds and entries, accessibility identifiers and launch argument names. The UI tests compile these too |
| `DesignSystem/` | Color, type and spacing tokens, and the few components the app adds to system controls |

## Rules the app follows

- Each window has its own app coordinator; the `App` holds no navigation state, only the shared services.
- `AppServices` holds only what lives as long as the app.
- The app and its unit tests are main actor by default, so they write no `@MainActor` (see [`CODE_STYLE.md`](../CODE_STYLE.md)).
- Screens report through callbacks; only coordinators navigate, with `make…Flow()` to build and `show…()` to navigate.
- Accessibility identifiers follow one pattern: `<flow>.<screen>` for journeys, and `root.<branch>`, `<branch>.<flow>.<kind>`, `placeholder.<flow>.<kind>`, `lab.story.<story>` and `lab.detail.<screen>` in the Lab.
- The code follows the package's code style in [`CODE_STYLE.md`](../CODE_STYLE.md).

# Changelog

All notable changes to Waypoint are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## Unreleased

### Changed

- The example app hides the tab bar from its stacks instead of from each screen. `ScreenChrome` no longer guessed from a screen's trail whether it was pushed, and tab roots no longer sent their own tab-bar value that competed with the pushed screen's. The Shop and Search stacks use `tabBarOnPushedScreens(.hidden)`, the Account tab's plain stack hides it on its pushed screens, and screens in sheets and full-screen covers send nothing. `JourneyTests.testOrdersPushDetail` checks the Account tab hides it on a push and shows it again on its root. This also fixes `StackTests.testPushAndBack` on iOS 17, where the root's value won and the bar showed on a pushed product. (#207)
- The example app's Lab view model (`LabProductModel`) lives in its own file that imports only `WaypointCore`, and keeps a `NavigationOutcome` instead of display text; the view says it in words. The UI test for those screens is renamed `ViewModelStyleUITests`, so its name says it is a UI test. (#179)
- The route registry is strict in every build: a route type with no registered destination fails with `unregisteredRoute` and runs its fallback, even before anything is registered. Tests and previews ask for `RouteRegistry.permissive` in the root's `NavigationConfiguration`; registering never changes the mode (`RouteRegistry.Mode`, `strict`, `permissive`, `allows(_:)`). (#144)
- Settings for the whole tree are given once to the root router in one `NavigationConfiguration` (logging, `maxQueuedChanges`, a starting `registry` and `onNavigationFailure`), passed as `configuration:` to `StackRouter`, `TabRouter` and, later, `RootRouter`. Every router reads it through `configuration`, and none can change it: `setLogging(_:)`, `setMaxQueuedChanges(_:)`, `onNavigationFailure(_:)` and the `logging` and `maxQueuedChanges` properties are removed from routers. A queue limit below 1 reports `invalidSetting` at the root initializer's documented `file` and `line` and uses 32. Fallbacks and presentation defaults stay on every router. (#143)
- Source file headers name the author with their own email instead of the GitHub noreply address. (#140)
- `scripts/check-comment-width.sh` has the same file header as every other file. (#187)

### Added

- `tabBarOnPushedScreens(_:)` chooses whether the tab bar shows on the screens pushed onto the `WaypointStack`s inside a view, as `hidesBottomBarWhenPushed` does in UIKit. The stack applies it around every pushed screen, the missing-destination screen included, and never to its first screen. The default is the system's (`.automatic`, the bar stays), and the stack's value wins over one a screen sets inside itself. iOS only; other systems ignore it. (#207)
- A route whose type the router knows but no screen inside its stack registered, such as one registered only in another stack or listed only in the root's registry, no longer shows SwiftUI's empty screen. When the push ends, or once a restored stack appears, `WaypointStack` reports the new `missingDestination` issue once per type at `.fault`, in every build, with the fix in its message, and keeps the path. Debug builds show a "No destination for …" screen that names the route type and the `.destination(_:_:)` line to add; release builds show a blank screen; both keep the Back button. `missingDestination(_:)` chooses your own screen for every build, and gets a `MissingDestination` (`route`, `issue`, `routeTypeName`). The stack reports it through the new `package` call `rendererFoundNoDestination(for:)`. The example app's `MissingDestinationTests` push such a route from the product page, and `scripts/test-mac.sh` runs them again in the release configuration. (#166)
- Unified log and signposts: `OSLogHandler` writes Waypoint's lines to `os.Logger`, one category per `LogCategory` under the subsystem `<bundle identifier>.waypoint` (`OSLogHandler.defaultSubsystem`, overridable), each as one already-redacted public string, and draws every `LogInterval` as an `OSSignposter` interval. `LogConfiguration.osLog(subsystem:minimumLevel:revealsPrivateValues:)` builds a configuration for it. It lives in the internal `WaypointOSLog` target, which compiles empty without `os` and is re-exported by `Waypoint` and `WaypointUIKit`. A `LogConfiguration` made without a handler now uses the platform's default (`handler` is optional, `usesDefaultHandler` says so): `WaypointStack` writes such a tree to the unified log at `.notice` before it draws, while a handler the app gave, `.disabled` included, is kept. Each push the stack animates is a `push` interval in `renderer`, and a change held until a transition ends on iOS 17 logs `heldChange` at `.debug`. Property-wrapper issues use the same subsystem. The Events and logging article has the `log stream` commands and the intervals. (#78)
- The example app's Navigation Lab has a Views and view models section, one screen per story on the design canvas: Navigation style (VM-01) runs a demo product with outputs, an injected `FlowNavigator<LabShopFlow>` or `@FlowNavigation`, each pushing the same cart; Navigate after the flow is gone (VM-02) closes the product while its view model loads reviews, and the late push returns `.ignored`; A wrapper with no router above it (VM-03) shows `@StackNavigation` failing with `noRouterInScope` in a plain SwiftUI stack; and Preview a screen without the app (VM-04) shows the `.waypointPreview(flow:)` previews in the demo's source. Each demo runs full screen on its own `WaypointStack(flow:)`. `ViewModelStyleUITests` covers them. (#179)
- The example app's checkout runs on Waypoint (`WaypointStack(flow: CheckoutFlow.self)`, a fresh `StackRouter` for each checkout) in three pushed steps, Address, Payment and Review, as on the design canvas. The address step lists the saved addresses with one chosen; Add a new address pushes a form whose Save goes back, chooses the new address and shows an "Address saved" toast, and Save for next time keeps it in the address book, which Account, Addresses shares. `testCheckoutAddsAddress` covers it. (#183)
- The example app draws its products as the design canvas does: an illustration for each of the six products (drawn in SwiftUI by `ProductIllustration`) on Shop's cards and rows, Search, the cart, the wish list, the related product and the product page's wide hero. Shop opens with a "Nebula nights" collection banner that pushes the collection on the Shop stack (`CollectionRoute`), then two products picked as cards and the rest as rows. The catalog, categories and prices match the canvas, and the tab bar hides on every pushed screen. UI tests open the collection from the banner and check the tab bar on a push and back. (#182)
- `.mise.toml` pins the developer tools (Tuist, SwiftLint and Periphery), and `scripts/bootstrap.sh` installs them: `mise install` on a Mac, or the pinned SwiftLint with its sha256 checked on Linux, where mise can't run. `CONTRIBUTING.md` has the setup steps. (#80)
- Navigation from views and view models: `StackNavigator` and `FlowNavigator<Flow>` are handles that navigate a stack and own nothing. A view model takes one, imports only `WaypointCore`, and is tested with a real router. They hold their router weakly: once their flow is gone every call returns `.ignored` and logs `staleNavigator`, and `isActive` is `false`. `router.navigator`, `router.navigator(for: ShopFlow.self)` and `navigator.scoped(to: ShopFlow.self)` make them. A flow navigator only pushes and pops to its flow's routes, checked by the compiler (`unscoped` is the escape hatch, and `present` takes any route). `router.declareFlow(_:)` and `declaredFlow` say which flow a stack shows, and asking a declared stack for another flow's navigator reports `flowMismatch` and still works. SwiftUI: `WaypointStack(flow:router:root:)`, a `destination(_:_:)` closure that also takes the stack's navigator, the optional `@StackNavigation`, `@FlowNavigation(Flow.self)` and `@DismissFlow` (`DismissFlowAction`) wrappers, `@Environment(StackRouter.self)` inside a stack, and `waypointPreview()` / `waypointPreview(flow:)`. A wrapper with no matching stack above its view fails each call with `noRouterInScope`, names its file and line and the fix, and logs a fault; nothing crashes. `scripts/check-compile-failures.sh`, run by `scripts/test-linux.sh`, proves that pushing another flow's route doesn't compile. (#25)
- `WaypointLink`: a view that pushes a route onto the nearest `WaypointStack` when tapped, with the same arguments as `NavigationLink(value:)` (`init(value:label:)`, `init(_:value:)` with a localized or plain title), so moving a view onto Waypoint is a rename. A tap calls `push` on the stack's router, so the duplicate push rule, the strict registry and fallbacks apply, and an optional `else:` picks the link's own fallback; logs name the line that made the link. A `nil` value or a link outside a Waypoint stack is disabled. A system `NavigationLink(value:)` inside a stack is still refused and reported as `rendererMismatch` at `.error`, in release builds too, and its message names `WaypointLink`. The SwiftUI renderer article has a migration note. The example app's product page links to a related product with it, and logs navigation issues to a banner; UI tests check the link pushes through the router and that a system link is reported, with `scripts/test-mac.sh` running that check again in the release configuration. (#147)
- One push per tap: while a stack still animates a push, a second push of an equal route changes nothing and returns `.alreadyThere`, so a fast double tap on a row pushes one screen. The readable log names the skipped push at `.debug` ("skipped: … is still being pushed"), and the structured line adds `skippedPush=`. On by default; `setDuplicatePushRule(.allow)` on a `StackRouter` or `TabRouter` turns it off for that flow and its children (`DuplicatePushRule`, `duplicatePushRule`). The SwiftUI stack reports when a push starts and ends through the new `package` calls `rendererDidStartPush(of:)` and `rendererDidEndPush(of:)`; without a renderer every push goes ahead. The example app has a UI test that double taps a product row. (#142)
- `NavigationFallback.replacePresentation`: a `present` made while a flow is already presented dismisses that flow and everything above it, then presents the new route with the call's style, in one change (`recovered alreadyPresenting by=replacePresentation`). On any other call it fails with `fallbackFailed`, and a replacement made in code never asks for a leave confirmation. `NavigationOutcome.didChange` answers whether a call changed the state, next to the existing `failure`. The Presentation and Stack navigation articles show both. (#145)
- Route hints: routes carry identity and the coordinator supplies the model. A `@RouteHint` field lets a list hand over what it already loaded, such as `ProductRoute(id: product.id, preview: product)`, so the next screen shows it at once. A hint is never saved (encoding leaves the key out, and decoding, restoring or a link gives `nil`), never compared or hashed, and never described, even with private values revealed. The value needs only `Sendable`. The Routes article shows the pattern, and the example app's product list passes its product as the hint. (#146)
- SwiftUI stacks: `WaypointStack` draws a `StackRouter` with one `NavigationStack`, and `destination(_:_:)` registers one screen per route type, so screens are never wrapped in `AnyView`. Pushes, multi-step pushes, pops and pop to root draw as one animation each, and a swipe back or the Back button menu comes back to the router as a user pop. On iOS 17 a change that lands while a push or pop still animates is held and the newest path is shown when it ends. A `NavigationLink(value:)` push is refused and reported as `rendererMismatch`. The example app's Shop and Search tabs run on it, with UI tests for push, back, swipe back, a three-product push, and a pop, pop to root and link 150 ms into it. (#11)
- Renderer reports: what the user changes directly (swipe back, the back button and its long-press menu, a sheet dragged down, a tab tap) comes back to the router through `package` calls (`rendererDidPop(toCount:)`, `rendererDidDismiss()`, `rendererDidSelect(_:)`) that run like any change and are logged with `origin=user` ("· by user" in the readable log). A report that matches the state changes nothing, and a stack count the path can't match keeps the path and reports the new `rendererMismatch` issue. (#38)
- Swift package with three products: `WaypointCore` (UI-agnostic state engine), `Waypoint` (SwiftUI renderer) and `WaypointUIKit` (UIKit renderer). (#2)

The README and the example flows lead with it, and the `@SwitchRoot` property wrapper is removed: screens report, the app coordinator switches the root. (#8)

- `RouteKey`: a route's key is its module and type name, such as `Shop.ProductRoute`, so routes declare no keys and two routes can't share one. Renamed routes list old keys in `formerRouteKeys`. The registry reports `duplicateRouteKey`, `unstableRouteKey` and `invalidRouteKey` at launch, and logs print the key's `typeName`. (#8)

- Typed routes: the `Route` protocol, `RouteKey` from the module and type name, `formerRouteKeys` for renames, `publicLogFields`, `NavigationFlow` and `AnyFlow`, the type-erased `AnyRoute`, `RouteRegistry` with its launch checks (`duplicateRouteKey`, `unstableRouteKey`, `invalidRouteKey`), `RouteDecodingError`, and `NavigationDescribable` with private-by-default route descriptions. Erased routes save as their key and value, and decode through the registry in `decoder.userInfo[.routeRegistry]`. (#10)
- Navigation state values: `FlowID`, `StackState`, `TabState`, `Presentation` (with the presented flow's root route), `PresentationStyle`, `SheetDetent`, `SheetOptions`, `NavigationTree` and `NavigationChange`, all with stable one-line descriptions. Pure reducers for stack, presentation and tab commands, and `RouteTable`, the type-keyed destination table that also registers each route type for decoding. (#45)
- `StackRouter` and `TabRouter<Tab>`: `@MainActor @Observable` owners of a stack and a tab container. Push, pop, `popTo`, `popToRoot`, present a route as a child flow with its own router, `dismiss`, `dismissAll`, `dismissFlow`, tab selection with pop-to-root on reselect, `setTabs`, inherited `presentationDefaults`, and the `NavigationRouter` tree (`parent`, `children`, `root`, `isActive`). Every call returns a `NavigationOutcome` (`applied`, `alreadyThere`, `queued`, `ignored`, `failed`) with a `NavigationIssue` that names the caller's file and line. Calls made while a change is applied are queued and run in order, up to `maxQueuedChanges` (`reentrantLoop`), and routers that left the tree return `.ignored`. (#46)
- Transactions: `transaction { }` on `StackRouter` and `TabRouter` applies several steps as one change through `NavigationTransaction`, across tabs and presented flows, and rolls everything back when a step fails. Path helpers: `@RoutePathBuilder` with `push { }` and `setPath { }`, `popTo(_:where:)` by type, `contains(_:)` and `last(_:)`. (#47)
- Fallbacks: every navigation call and transaction step takes `else:` with a `NavigationFallback` (`none`, `popToRoot`, `push`, `dismissAll`, `resetToRoot`, `custom`), chosen before the router's inherited `fallbackPolicy` and the built-in default (`.popToRoot` only for popping more routes than the path holds). A fallback runs once in the same change, with its changes marked as coming from a fallback; if it fails too, the call is rolled back and `onNavigationFailure` handlers get one `NavigationFailure` with both issues. Outcomes gain `.recovered`. (#85)
- Logging seam: `LogLevel`, `LogCategory`, `LogMessage`, `LogInterval`, the `LogHandler` protocol with `DisabledLogHandler`, and `LogConfiguration`, set once per tree with the router's `logging` property. The core logs applied changes at `.info`, no-op, queued and ignored calls at `.debug`, recovered issues at `.error` and failed calls at `.fault` with their call site, and measures each transaction as one interval. Messages are built only when enabled, and route values stay private unless listed in `publicLogFields`. (#77)
- The API articles show the `else:` fallback argument on every navigation call, and the README shows a fallback in one line. (#85)

Transactions and custom fallbacks take `NavigationTransaction` by value instead of `inout`. Every remaining `var` says why it can't be `let`. (#8)

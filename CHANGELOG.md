# Changelog

All notable changes to Waypoint are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## Unreleased

### Added

- Child flows can be pushed (#59, fifth part). `router.push(child) { result in … }` and the lazy `router.push(onFinish:) { child }` show a `FlowCoordinator`'s screens on the parent's stack: the parent's path holds one route for the child's root screen, and the child's router, a child of the parent in the tree, keeps its own path. Going back past the child's root screen, or a push, pop or `popTo` on the parent, ends the child with `.cancelled` first; `finish(with:)` and `dismissFlow()` pop back below it. The duplicate push rule skips a second push of the same flow while its push is still animating. Both push forms are public in `Waypoint` and take a `FlowCoordinator`, so the compiler checks that the pushed flow has screens to draw. The stack draws its router's drawn path, the parent's path followed by the pushed child's: the child's `root` and `destinations` are drawn for its marker, its screens see the child's router (`@StackNavigation`, `@DismissFlow`, the navigators handed to its destinations), and Back or a swipe goes to the router that owns the screen, so going back past the child's root ends it. A destination's screen now sees the stack router of the screen that declared it. A view controller screen (`ControllerScreen`) is made once, when SwiftUI first shows it, never on a redraw. Orbit Shop's Lab Detail push product has Write a review, the first pushed child flow (`DetailReviewCoordinator`), which finishes with the stars the product then shows. New `DrawnPathTests` (7 tests, such as `drawnPathFollowsTheMarkerWithTheChildsPath`, `theSameFlowPushedAgainGetsANewMarker`, `backPastTheChildsRootEndsItCancelled` and `aGrandchildsScreensFollowItsParentsOnTheOneStack`), `StackMirrorTests.showsAPushedChildFlowsScreensAfterItsMarker`, `backInsideAPushedChildFlowPopsTheChild` and `aChildFlowsPushIsReportedToTheChild`, and in the example app `DetailReviewCoordinatorTests` (3 tests), `LabTests.testPushedReviewFlowFinishesOnTheSameStack` and `testPushedReviewFlowLeftWithBackCanStartAgain`. In debug builds a pushed flow that can't be drawn shows why (`waypoint.pushedFlow.missing`). `PushedChildFlowTests` (13 tests, such as `doubleTapPushesTheFlowOnce`, `rolledBackPushLeavesChildAsItWas`, `pushingChildFlowNestsRouter`, `pushedFlowReleasedOnPop`, `finishPopsBelowTheChildsRootScreen`, `parentPushEndsTheChildOnTop` and `flowRoleDecidesHowItIsBuilt`).
- Stack and flow coordinators draw their own screens (#59, fourth part). A `StackCoordinator` or `FlowCoordinator` writes its `root` screen and its `destinations`, built from `Destination(Route.self) { route in … }` entries, and shows its whole flow with `view`, drawn by `SwiftUIStackRenderer` (`DefaultStackRenderer`), a `WaypointStack` on the coordinator's router. A screen is a SwiftUI view or, where UIKit is, a view controller (`@ScreenBuilder`). Every route type in `destinations` is registered when the router is made, so no `register(_:)` calls remain and a push from `init` is never refused. A coordinator with one screen leaves out `destinations`. A coordinator's `view` drawn in two places at once is reported as `coordinatorDrawnTwice`. A coordinator picks another renderer with `typealias Renderer`, a `StackRenderer`. Orbit Shop's Lab Detail push and Tabs story coordinators draw themselves with `view`, and Reset password's screen is its coordinator's `root`. New tests: `coordinatorDrawnTwiceIsReported`, `viewReplacedInOneUpdateIsNotReported` and `coordinatorsSharingOneStackAreNotReported`, the new `CoordinatorScreensTests` (6 tests, such as `destinationsRegisterEachRouteWithItsScreenName`, `coordinatorWithOnlyARootHasNoDestinations` and `eitherBranchOfARootIsNamedByItsFirstScreen`), and in the example app `destinationsRegisteredWithoutRegisterCalls`.
- Child flows end with a result (#59, third part). Conforming to `FlowCoordinator` (in `Waypoint`), or to `FlowCoordinating` (in `WaypointCore`), adds an `Output` and fills in `finish(with:)`. `router.present(child, style:) { result in … }` presents the child's flow from a stack or a tab router: the child's router joins the presenting router's tree, with any screens it pushed before, and the parent gets a `FlowResult`, `.finished(value)` or `.cancelled`, exactly once, after the call that ended the flow is done. `finish(with:)` delivers the value and dismisses the flow; a swipe, `dismissFlow()`, a parent's dismiss or the `.replacePresentation` fallback delivers `.cancelled`. Waypoint keeps the child until its flow ends, then lets it go. The lazy form, `router.present(style:onFinish:) { child }`, builds the child only when the present happens, and makes its router inside the parent's tree, so a push from the child's `init` gets the tree's settings; another router that took the child's place is reported as `routerDetachedFromLazyStart`. A present that fails or is ignored never calls `onFinish:`. A child whose router is the presenting router or one above it fails with the new `childRouterIsAncestor`, and one whose router is already in another tree with `routerInAnotherTree`. Orbit Shop's Reset password is the first child flow: `ResetPasswordCoordinator` finishes with the email the link went to, and the accounts flow presents it with `onFinish:`. New `ChildFlowTests` (38 tests, such as `finishDeliversValueToParent`, `userDismissDeliversCancelled`, `resultDeliveredExactlyOnce`, `lazyChildPushInInitUsesRootSettings`, `childReleasedAfterFinish`, `droppedParentReleasesAndCancelsItsChild` and `rolledBackStartLeavesChildAsItWas`) and, in the example app, `ResetPasswordCoordinatorTests.doneAfterSendingFinishesWithTheEmail`, `cancelEndsTheFlowCancelled` and `secondTapKeepsTheFlowOnScreen`.
- Tab coordinators store no router either, and each tab's stack is its coordinator's router (#59, second part). Conforming to `TabCoordinator` (in `Waypoint`), or to `TabCoordinating` (in `WaypointCore`), fills in the router: made with the coordinator's `makeRouter()`, which has no default, the first time it is read, and kept in the core's table. Then each tab's coordinator is asked for once, with `tabCoordinator(for:)` (`coordinator(for:)` in the core), and kept as long as the tab coordinator and its tab are; a tab `setTabs` adds later gets its coordinator then, and a removed tab's coordinator is let go (one the app keeps and returns again gets the tab's new stack). A router made on its own can now join another tree, with its path, screens and registered routes: each tab's coordinator's router becomes the tab's stack, and the stack it replaces forwards to it, so a navigator taken before keeps working; a tab's stack that already has screens, such as one the tab's coordinator pushed on in `init`, is kept, and the coordinator's own router forwards to it instead. With `TabRouter(stacks: .shared)`, the selected tab's coordinator is asked first and its router becomes the shared stack, every other tab's coordinator drives that stack, and the journey names the shared stack after the selected tab's coordinator. New issue kinds: `coordinatorDrawnTwice` (one coordinator returned for two tabs), `routerInAnotherTree` (a tab's coordinator whose router is already in another tree) and `tabChildRouterMerged` (screens a tab's coordinator pushed or presented on its own router before it joined, dropped because the tab keeps the shared stack or a tab stack that already had screens); each refused tab keeps a stack of its own. A tab coordinator that stores `let router` is reported as `routerNotFromWaypoint` when `navigator(for:)` is taken, and adopted. The Navigation Lab's Tabs story is the first to conform, with a coordinator for each tab. `ViewModelStyleUITests.testLatePushAfterBackIsIgnored` no longer races the reviews: the new `-labReviewsSeconds` launch argument gives it 8 s, and it waits for the demo to close first. New `TabCoordinatingTests` (41 tests, such as `tabCoordinatorHandsChildrenTheirRouters`, `tabChildPushInInitKeepsItsRouter`, `sharedStackMergesLaterChildRouter`, `sharedStackAsksSelectedTabFirst`, `removedTabReleasesItsChild` and `tabChildrenReleasedWithTabs`) and, in the example app, `TabsDemoCoordinatorTests.eachTabStackIsItsCoordinatorsRouter` and `addedTabsGetTheirCoordinatorsAndRemovedTabsLeave`.
- Stack coordinators store no router (#59, first part). Conforming to `StackCoordinator` (in `Waypoint`), or to `StackCoordinating` (in `WaypointCore`, for code with no UI), fills it in: the router is made with `makeRouter()` the first time it is read, named after the coordinator, rooted at `rootName` (the type's name without `Coordinator`, or the one the coordinator declares, which replaces a root name the router came with; a different name `makeRouter()` set is reported as `rootNameReplaced`), given the coordinator's `registerDestinations(on:)`, and kept in a table the core owns, which holds the coordinator weakly. Once the coordinator is gone, the next read or navigation call, its own included, drops its router and, when the table made it, makes it inert with every flow it presents (a router ends with its coordinator: handed to a later one, from `makeRouter()` or stored, it is reported as `releasedRouterReturned`), so a navigator kept past the flow returns `.ignored` from its first call and logs `staleNavigator`. A coordinator that stores `let router` is reported as `routerNotFromWaypoint` the first time Waypoint touches it, such as by its default `navigator` or `navigator(for:)`, and its router is adopted; a stored router another coordinator owns is reported as `routerOwnedByAnotherCoordinator` and left with its owner. A router read in `deinit` is inert. The Navigation Lab's Detail push coordinator is the first to conform, making its router from the Lab's configuration. New `StackCoordinatingTests` (25 tests, such as `routerMadeOnFirstRead`, `storedRouterIsReportedAndAdopted`, `madeRouterOfAnotherCoordinatorIsNotAdopted`, `freedCoordinatorLeavesNoRouter`, `reusedIdentifierGetsAFreshEntry` and `readInDeinitOfACoordinatorWithARouterGetsItInert`) and, in the example app, `DetailPushCoordinatorTests.routerIsMadeForTheDetailPushFlow` and `closedDemoLeavesNoLiveRouter`.
- Orbit Shop has one services container with a dependency struct for each feature (#301). `AppServices`, now in `Dependencies/`, takes its store and product catalog through its initializer, and gives `ProductsDependencies`, `CartDependencies`, `AccountDependencies`, `AuthDependencies` and `LabDependencies`, each listing only what its feature uses; the coordinators move onto them with #59. `LocalStore(domain:)` gives a test its own data, and `ProductCatalog` (with `SampleCatalog`, the sample products) is the seam the screens move onto next. The app and its unit tests are main actor by default (`SWIFT_DEFAULT_ACTOR_ISOLATION`), so the app writes no `@MainActor`, and `scripts/check-example-isolation.sh` checks that on every run. New unit tests: `AppServicesTests.clearAllDataResetsEveryService` and `screensShareOneAppWideStore`, `LocalStoreTests.testsNeverTouchAppData` and `testStoreStartsEmpty`.
- Apps write one import (#304). `Waypoint` re-exports `WaypointCore`, so `import Waypoint` alone gives routes, routers and outcomes. Code that draws nothing may import `WaypointCore` alone. Orbit Shop now imports one of the two in each file, the README's examples show one import, and `scripts/check-single-import.sh` fails when an example app file or a docs snippet imports both, or an example app file imports `WaypointCore` next to SwiftUI or UIKit. New `OneImportTests.waypointAloneGivesCoreTypes`.
- `TabRouter(stacks: .shared)` lets the tabs share one stack above the tab bar, drawn with `WaypointStack` around the `TabView`. Pushed screens then slide in over the tab bar, the system's own way, and the bar leaves and comes back with the tab's root, also on a swipe back. Selecting another tab, or removing the selected one, pops the pushed screens, and the journey box names the shared stack after the selected tab. `TabStacks.perTab`, one stack per tab, stays the default. ### Changed

- CI runs on Tuist runners (#332). Every job in `.github/workflows/ci.yml` uses `runs-on: tuist-linux` instead of `ubuntu-latest`, now that the repo belongs to an organisation, so CI spends the Tuist account's Linux minutes instead of GitHub Actions minutes. The check names stay the same.
- The repo now lives in the `joeoct-oss` organisation (#330). The README's install line is `.package(url: "https://github.com/joeoct-oss/Waypoint.git", from: "0.1.0")`, and the links in the Concurrency article, the PR and issue templates and the code name the new owner. The old URLs still redirect.
- A Mac run for one pull request gets Tuist's run report on that pull request (#337). `WAYPOINT_PULL_REQUEST=<n> scripts/test-mac.sh full` hands Tuist `GITHUB_REF=refs/pull/<n>/head`, and Tuist's GitHub app posts each `tuist test` command with its cache hit rate and the tests it ran and skipped. The script clears a stray `GITHUB_REF`, and a `coverage` run, an offline run or a merge batch of several branches names no pull request. New checks in `scripts/check-test-mac-lock.sh`, such as "tuist test gets the pull request's ref" and "a GITHUB_REF left in the shell never reaches tuist test".
- Tuist stays on its latest stable version unless the new one is breaking (#334). The pin in `.mise.toml` moves from 4.218.1 to 4.218.5, and the daily `scripts/test-mac.sh coverage` run prints `scripts/check-tuist-version.sh`, which says when a newer stable Tuist is out and whether it is a new major version (canaries and release candidates never count). TESTING.md says how the Mac's cache proxy follows a bump: `tuist teardown cache`, then `tuist setup cache`, since setup alone never moves the proxy to an older Tuist.
- The Tuist dashboard shows code coverage and the branch of every Mac run (#327). Every run that uses Tuist collects coverage and uploads it (`Example/Tuist.swift`: coverage on, with prefix mapping so the compilation cache keeps working), except the release reports step, which also builds into its own derived data folder so Tuist reads the example run's coverage from its Debug products, and the new `scripts/test-mac.sh coverage`, run once a day on `main`, runs every example test on `main`'s own commit and marks it complete (`tuist coverage complete`), so the Code Coverage page charts `main`. `scripts/test-mac.sh` tells Tuist the branch it tests through `GITHUB_HEAD_REF`: on a merge batch, its branches joined with `+`, where Tuist showed "Unknown" before. The Build Insights post-action runs the Tuist `.mise.toml` pins, through `mise exec`, instead of the first Tuist on the PATH. `tuist test` gets the example app's derived data folder as `-derivedDataPath` after `--`, as Tuist asks, and the log reads "release reports selective testing off" (#326).
- Mac merge runs skip example app tests that already passed on the same inputs (#324). The example app takes the package through Tuist's package integration (`Example/Tuist/Package.swift`), so Tuist's selective testing hashes the package's sources and runs the app's tests again after any change to them; before, it hashed the package by its product names only. `scripts/test-mac.sh full` now uses selective testing too, unless the branch changes a file the hashes don't cover (a script, a manifest, a tool version, CI); `release`, `--only`, `--ui` and `--all` still run every test. The new `scripts/check-selective-testing-hashes.sh`, part of `full` and `release`, checks that an edit in each package module and in the app changes the hashes. The package's own scheme steps, and the docs build, run xcodebuild through the new `scripts/package-xcodebuild.sh`, which moves Tuist's generated `Waypoint.xcodeproj` and `Derived/` aside while they run. `tuist test` runs with `--no-binary-cache`, so the package is always built from source with warnings as errors.
- Test runs report more and wait less (#5). The Linux checks container runs with an init process (`--init`), so the run lock check no longer waits on processes nobody reaps: about 36 s instead of 75 s on GitHub. `scripts/test-mac.sh` writes a result bundle for the package's simulator tests too, so the report lists their slowest tests like the example app's. `scripts/check-merge-batch.sh` names a branch that fails to merge with a merge commit instead of stopping silently. TESTING.md records the measured selective testing and simulator copy results.
- Pull requests merge by squash by default, or with a merge commit (same title format) when the branch's commits explain why the change was made; rebase merges are off. `main` no longer requires linear history (#320). `scripts/check-merge-batch.sh` also checks that a batch merged with merge commits ends on its tested tree (#321).
- Pull requests to `main` get CI (#5): `.github/workflows/ci.yml` runs `scripts/test-linux.sh` as the **Linux checks** check on GitHub Actions when a pull request is ready for review and on each push after that (drafts are skipped, a newer push cancels the older run). It runs only when the repository variable `CI_ENABLED` is `true`. The Mac stays the full gate. Its checks are the Linux merge gate in `TESTING.md`: a hand run of `scripts/test-linux.sh` is needed only while `CI_ENABLED` is off, or when `main` moved after the check ran.
- CI does no work it doesn't need (#5). A pull request that changes only docs skips the Swift jobs (**Linux checks** and **Builds with Swift 6.2**), and a new first check, **Changed files and docs checks**, runs the two checks that read Markdown on every pull request. `scripts/test-linux.sh` builds once with warnings as errors and runs the fixture check and the tests on that build, instead of building the same code twice more.
- The package needs Swift 6.2 or later (Xcode 26 or later): `Package.swift` now says `swift-tools-version: 6.2`. The code already used `weak let`, which arrived in Swift 6.2, so a Swift 6.0 build failed; CI now builds with Swift 6.2 on every pull request. (#316)
- Pull requests merge in batches (#295): `scripts/merge-batch.sh <branch>...` stacks up to four ready pull requests on the latest `main` in the Mac clone, without pushing, so one `scripts/test-mac.sh full` run covers them all, `--before-merge` stops the batch before any merge when a branch or `main` moved since the run, and `--after-merge` checks that `main` ends on the tested tree. `scripts/test-mac.sh` writes a result bundle for each example app test step and ends with its 10 slowest tests (`scripts/slowest-tests.py`). `scripts/check-merge-batch.sh` checks both in a temporary repository, and `scripts/test-linux.sh` runs it. `TESTING.md` has the batch steps and the report's new lines, and CONTRIBUTING's review and merge section links to them.
- `scripts/test-mac.sh` takes one run lock as its first step (#294), `/tmp/waypoint-test-mac.lock`, which every clone on the Mac shares, so a second run stops at once and names the run that holds it instead of slowing both down and failing tests. A lock whose run has ended is cleared, and a live run's lock is never touched. The new `scripts/check-test-mac-lock.sh` checks the lock with stand-in tools, and `scripts/test-linux.sh` runs it. `TESTING.md` describes the lock, its error and its preflight check, and records that nothing merges without a green `full` run on a commit that contains the latest `main`.
- `TESTING.md` is the one home for running the tests (#286): where each test layer runs (Linux or the Mac), which run is needed while working, before a merge and before a tag, the three simulators (`waypoint-01`, `waypoint-02`, `waypoint-03`), step-by-step preflight, run, pass line and teardown for `scripts/test-linux.sh` and `scripts/test-mac.sh`, a table of failures and what to do for each, and the report every run ends with. CONTRIBUTING links to it instead of listing the commands, and the pull request template asks for the merge gate's report. A comment in `Example/Project.swift` is wrapped at 100 columns, so `scripts/test-linux.sh` passes again.
- The draft API articles and the README show one coordinator for each kind (`RootCoordinator`, `TabCoordinator`, `StackCoordinator`, `FlowCoordinator`), written once for SwiftUI and UIKit apps: `root` and `destinations` take SwiftUI views or UIKit view controllers, `view` and `viewController` draw the whole flow, and `WaypointRoot { … }` or `makeWindow(for:options:)` make the window. `SwiftUIStackCoordinator`, `UIKitStackCoordinator`, `SwiftUIRootCoordinator` and `UIKitRootCoordinator` are gone from the drafts. A new Coordinators and renderers article covers the renderer for each kind, the SwiftUI defaults, choosing a renderer app-wide or per coordinator, and writing your own. The UIKit articles move into the `Waypoint` catalog, and the docs site builds two catalogs. The Presentation article drafts a destination's declared presentation and `router.show(_:)`. Docs only. (#251)
- `scripts/test-mac.sh` runs the example app's tests through `tuist test`, on 2 temporary copies of the simulator at once (`WAYPOINT_UI_WORKERS`), so a full run's longest step takes about half as long (#312). The example app is linked to its Tuist server project, so `tuist test` uses Tuist's binary cache, and, in `quick` runs of branches that change only `Example/`, its selective testing, and sends test results and build timings to the project's Tuist dashboard (`WAYPOINT_TUIST_OFFLINE=1` turns all of it off).

- `scripts/test-mac.sh` runs in tiers so it loads the Mac far less (#247). `quick`, the default while working, runs the guard rail, the compile fixtures, the host tests and the simulator package tests, each built once with warnings as errors, and the example app's UI tests only when the branch changes `Example/` or a renderer; it skips what the branch can't affect (`--ui`, `--all` and `--only <test>` override). `full`, before every merge, runs every check whatever changed. `release`, before a tag, adds the iOS device build and the package and example tests on the iOS 17 simulator (`WAYPOINT_IOS17_SIMULATOR`, default `waypoint-02`). Builds use at most `WAYPOINT_JOBS` jobs (default half the performance cores), Xcode never clones the simulator, one run holds a simulator at a time, the script shuts down each simulator it booted, and it ends with the time of each step. `scripts/check-compile-failures.sh` builds with `WAYPOINT_SWIFT_BUILD_FLAGS`, so the Mac script's core build is reused.

### Fixed

- A failure handler that navigates no longer crashes the app after `maxQueuedChanges` calls were queued. The refused call called the handler, whose call was refused again, without end. Now `reentrantLoop` is reported once per outermost call and later refusals are dropped quietly. (#24)
- Observation observers no longer see a transaction that changes two routers half applied: every router announces its change before any of them changes its state. (#24)
- On iOS 17, a change made while a push was still being drawn on a busy device, such as a pop soon after a multi-step push, is no longer lost. The stack's transition hold counts from when the main thread is free after drawing, not from the path change. (#204)
- The example app's UI tests close iOS's "Save Password?" offer after a sign in (#299). On iOS 27.2 it covered the app after `NestedSheetTests.testDoneClosesAllSheets` signed in, so its later taps missed. The step waits for the offer to show and then to go, since it still covers the app while it slides away; on iOS 17 it doesn't wait.
- The example app's sheet size UI tests drag a medium sheet up by its grabber, up to 3 times, to grow it to large (#307). On iOS 27.2 one swipe up on the sheet's navigation bar often left it at medium.

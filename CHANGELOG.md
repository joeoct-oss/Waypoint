# Changelog

All notable changes to Waypoint are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## Unreleased

### Changed

- The route registry is strict in every build: a route type with no registered destination fails with `unregisteredRoute` and runs its fallback, even before anything is registered. Tests and previews ask for `RouteRegistry.permissive` in the root's `NavigationConfiguration`; registering never changes the mode (`RouteRegistry.Mode`, `strict`, `permissive`, `allows(_:)`). (#144)
- Settings for the whole tree are given once to the root router in one `NavigationConfiguration` (logging, `maxQueuedChanges`, a starting `registry` and `onNavigationFailure`), passed as `configuration:` to `StackRouter`, `TabRouter` and, later, `RootRouter`. Every router reads it through `configuration`, and none can change it: `setLogging(_:)`, `setMaxQueuedChanges(_:)`, `onNavigationFailure(_:)` and the `logging` and `maxQueuedChanges` properties are removed from routers. A queue limit below 1 reports `invalidSetting` at the root initializer's documented `file` and `line` and uses 32. Fallbacks and presentation defaults stay on every router. (#143)
- Source file headers name the author with their own email instead of the GitHub noreply address. (#140)

### Added

- SwiftUI stacks: `WaypointStack` draws a `StackRouter` with one `NavigationStack`, and `destination(_:_:)` registers one screen per route type, so screens are never wrapped in `AnyView`. Pushes, multi-step pushes, pops and pop to root draw as one animation each, and a swipe back or the Back button menu comes back to the router as a user pop. On iOS 17 a change that lands while a push or pop still animates is held and the newest path is shown when it ends. A `NavigationLink(value:)` push is refused and reported as `rendererMismatch`. The example app's Shop and Search tabs run on it, with UI tests for push, back, swipe back, a three-product push, and a pop, pop to root and link 150 ms into it. (#11)
- Renderer reports: what the user changes directly (swipe back, the back button and its long-press menu, a sheet dragged down, a tab tap) comes back to the router through `package` calls (`rendererDidPop(toCount:)`, `rendererDidDismiss()`, `rendererDidSelect(_:)`) that run like any change and are logged with `origin=user` ("· by user" in the readable log). A report that matches the state changes nothing, and a stack count the path can't match keeps the path and reports the new `rendererMismatch` issue. (#38)
- Swift package with three products: `WaypointCore` (UI-agnostic state engine), `Waypoint` (SwiftUI renderer) and `WaypointUIKit` (UIKit renderer). (#2)
- `scripts/test-linux.sh` runs the core build and tests on Linux, after `scripts/check-core-imports.sh` checks that `WaypointCore` imports only Foundation, Observation and Synchronization. `CONTRIBUTING.md` explains how to run them. (#35)
- API design articles in the `WaypointCore` DocC catalog: Routes, Navigation state, Stack navigation, Presentation (with app-chosen sheet sizes) and Tabs. Signatures only; the API is implemented in later issues. (#42)
- API design articles for coordinators and child flows, root switching, events and logging, guards, deep links, state restoration, concurrency, and testing your navigation. Signatures only. (#43)
- DocC catalogs for the `Waypoint` (SwiftUI) and `WaypointUIKit` products, with renderer API articles, navigating from views and view models, and five example flows in each renderer. Signatures only. (#44)
- Every type in the API articles lists its conformances with a reason for each, and a new "Why these conformances" article explains `Hashable`, `Codable`, `Sendable`, `Equatable` and `AnyObject`. (#8)
- The API articles now show restore options for skipping presentations, how an observer reads the whole tree after a change, and that the testing helpers work in both Swift Testing and XCTest. (#8)
- Switch cases in the API articles put their body on its own line. (#8)
- The app's navigation now lives in an app coordinator (`RootCoordinator`, `SwiftUIRootCoordinator`, `UIKitRootCoordinator`), drawn by `WaypointRoot(app)` or `WaypointRootViewController(app)`. The README and the example flows lead with it, and the `@SwitchRoot` property wrapper is removed: screens report, the app coordinator switches the root. (#8)
- UIKit: `UIKitRootCoordinator` gains `makeWindow(for:options:)` and `receive(_:)` forwards, so a scene delegate's lifecycle methods only hand the OS's input to the app coordinator. (#8)
- Root coordinators build each root with `makeFlow(for:)` in both renderers. Examples give every `case` one call to a named function: `make…Flow()` builds a flow, `show…()` navigates. (#8)
- Shared conformance sets have one name each: `NavigationValue`, `NavigationRecord` and `NavigationStateValue` for Waypoint's value types, and the `NavigationTab` protocol for an app's tab types (`NavigationRoot` comes with `RootRouter`). `TabState<Tab: NavigationTab>: NavigationStateValue` replaces four conformances and three constraints. (#8)
- `TabRouter(selection:)` for a `CaseIterable` tab type shows every case in declaration order; pass `tabs:` to show some of them or another order. (#8)
- No array, dictionary or set literal is written inside a call's arguments in the code, tests and articles: each one is named with `let` first. (#8)
- Wrapped calls in the code and the articles put each argument on its own line, with `)` alone on the last line, and coordinator closures call named functions such as `showProduct(id:)`. (#8)
- New "Descriptions" article and `NavigationDescribable`: routes, state, events, outcomes, issues and snapshots print one stable, logfmt-style line, with route fields private unless listed in `publicLogFields`. (#8)
- Examples in the API articles put a blank line between member groups, such as stored properties and the initializer, and around every member with a body. (#8)
- `RouteKey`: a route's key is its module and type name, such as `Shop.ProductRoute`, so routes declare no keys and two routes can't share one. Renamed routes list old keys in `formerRouteKeys`. The registry reports `duplicateRouteKey`, `unstableRouteKey` and `invalidRouteKey` at launch, and logs print the key's `typeName`. (#8)
- `SheetDetent.fitsContent` sizes a sheet to its content, up to `SheetOptions.fitsContentLimit` (default `.large`); taller content scrolls. (#8)
- Calls made while a change is being applied are queued and run in order (`.queued`, `reentrantChange`, `reentrantLoop` after `maxQueuedChanges`). Navigators whose flow is gone do nothing (`.ignored`, `staleNavigator`, `isActive`). The Concurrency article explains both. (#8)
- Every type in the API articles documents all of its members, not just some. (#8)
- Types in the core, the tests and the API articles list their members in one order (cases, aliases, nested types, static, stored and computed properties, initializers, lifecycle, static functions, functions), and wrapped signatures put each parameter on its own line. (#8)
- Every function, initializer, computed property and statement body in the API articles is on its own lines. (#8)
- Typed routes: the `Route` protocol, `RouteKey` from the module and type name, `formerRouteKeys` for renames, `publicLogFields`, `NavigationFlow` and `AnyFlow`, the type-erased `AnyRoute`, `RouteRegistry` with its launch checks (`duplicateRouteKey`, `unstableRouteKey`, `invalidRouteKey`), `RouteDecodingError`, and `NavigationDescribable` with private-by-default route descriptions. Erased routes save as their key and value, and decode through the registry in `decoder.userInfo[.routeRegistry]`. (#10)
- Navigation state values: `FlowID`, `StackState`, `TabState`, `Presentation` (with the presented flow's root route), `PresentationStyle`, `SheetDetent`, `SheetOptions`, `NavigationTree` and `NavigationChange`, all with stable one-line descriptions. Pure reducers for stack, presentation and tab commands, and `RouteTable`, the type-keyed destination table that also registers each route type for decoding. (#45)
- `StackRouter` and `TabRouter<Tab>`: `@MainActor @Observable` owners of a stack and a tab container. Push, pop, `popTo`, `popToRoot`, present a route as a child flow with its own router, `dismiss`, `dismissAll`, `dismissFlow`, tab selection with pop-to-root on reselect, `setTabs`, inherited `presentationDefaults`, and the `NavigationRouter` tree (`parent`, `children`, `root`, `isActive`). Every call returns a `NavigationOutcome` (`applied`, `alreadyThere`, `queued`, `ignored`, `failed`) with a `NavigationIssue` that names the caller's file and line. Calls made while a change is applied are queued and run in order, up to `maxQueuedChanges` (`reentrantLoop`), and routers that left the tree return `.ignored`. (#46)
- Transactions: `transaction { }` on `StackRouter` and `TabRouter` applies several steps as one change through `NavigationTransaction`, across tabs and presented flows, and rolls everything back when a step fails. Path helpers: `@RoutePathBuilder` with `push { }` and `setPath { }`, `popTo(_:where:)` by type, `contains(_:)` and `last(_:)`. (#47)
- Fallbacks: every navigation call and transaction step takes `else:` with a `NavigationFallback` (`none`, `popToRoot`, `push`, `dismissAll`, `resetToRoot`, `custom`), chosen before the router's inherited `fallbackPolicy` and the built-in default (`.popToRoot` only for popping more routes than the path holds). A fallback runs once in the same change, with its changes marked as coming from a fallback; if it fails too, the call is rolled back and `onNavigationFailure` handlers get one `NavigationFailure` with both issues. Outcomes gain `.recovered`. (#85)
- Logging seam: `LogLevel`, `LogCategory`, `LogMessage`, `LogInterval`, the `LogHandler` protocol with `DisabledLogHandler`, and `LogConfiguration`, set once per tree with the router's `logging` property. The core logs applied changes at `.info`, no-op, queued and ignored calls at `.debug`, recovered issues at `.error` and failed calls at `.fault` with their call site, and measures each transaction as one interval. Messages are built only when enabled, and route values stay private unless listed in `publicLogFields`. (#77)
- The API articles show the `else:` fallback argument on every navigation call, and the README shows a fallback in one line. (#85)
- Values are immutable and every change is checked. State, `SheetOptions`, `PresentationDefaults`, `LogConfiguration`, `FallbackPolicy`, `RouteRegistry` and `RouteTable` have only `let` fields and change through `with…` or `registering` functions; sheet options and tab states can't be made invalid, even when decoded. Routers replace their settable properties with guarded functions: `setLogging(_:)`, `setMaxQueuedChanges(_:)` (below 1 reports the new `invalidSetting` issue), `setPresentationDefaults(_:)` and `setFallback(_:for:)` (`.push` only for `routeNotInPath`); `popsToRootOnReselect` moves to the `TabRouter` initializer. Transactions and custom fallbacks take `NavigationTransaction` by value instead of `inout`. Every remaining `var` says why it can't be `let`. (#8)
- `README.md` with the Waypoint banner, a first look at the API, the products, requirements and links to every DocC article; an MIT `LICENSE`; and a complete `CONTRIBUTING.md` covering tests, code style, pull requests and merging. (#6)
- Example app scaffold in `Example/`, generated with Tuist: Orbit Shop, a small shop with a splash and main tabs that guests and signed-in readers share (Shop and Search with filter and wish list sheets, Cart with a count badge, a full-screen checkout and an order placed screen, Account with orders and settings). An action that needs an account (Check out, Save, Orders) presents a sign-in sheet (sign in, create account in three steps with a terms sheet, reset password) backed by a mock auth service, then carries on once the reader signs in. A local store keeps the session, cart and wish list, and Settings > Developer has Clear all data and the Navigation Lab with the five demo flows in both kinds. The `App` asks `AppCoordinator.makeWindow(services:launch:)` for each window's view, which gives every window its own app coordinator, and every screen uses system bars, tab bars, sheets and buttons. Includes the design system's color, type and spacing tokens, launch arguments that open any journey or Lab entry, and UI tests for the journeys and every Lab entry. `scripts/test-mac.sh` generates the project and runs them. (#3)
- The README shows what is built and what is designed, leads with routes, a router call with an `else:` fallback (output checked against the code), a flow, the app coordinator and a test, and links the Descriptions article. `CONTRIBUTING.md` lists every code style rule. (#19)
- Readable console logs, the new default: each line names the flow, then a symbol and a sentence, such as `shop       ▸ push Product list (…)`, with friendly route names, public fields shown and private ones folded into `…`. `LogFormat.structured` keeps the stable `key=value` lines for tools, `usesSymbols: false` drops the symbols, `TreeLogging` logs the changed stacks or the whole tree after each change, and `debugTree()` prints the whole tree. Issues are logged before the change their fallback made, issue messages show values when `revealsPrivateValues` is on, and structured presentation lines name the presenter as `presenter=`. (#117)
